# F-49 — The 512 KiB depth edge depended on which JIT tier ran the Resolver

- **Assumption** (F-44): with `MAX_IR_DEPTH = 512`, a filter 513 levels deep is a Stub on a fresh
  512 KiB thread in an agent-free child JVM, and 500 nested value parameters compile.
- **How it fails**: under load C2 lags and the Resolver runs C1-compiled. Each level then took about
  832 B of frames (`lower`, `built`, `array`), so 512 levels needed about 528 KiB and the thread
  overflowed about 500 levels down, before the 513-level Stub. C1 also inlined `Stub.unbuilt`'s
  string concatenation through `spend()` into `call` and `expand`, which overflowed 500 nested value
  parameters. `IrDepthTest.onA512KiBThreadInAFreshJvm512LevelsRunAndDeeperFiltersAreStubs` failed
  2 of 4 runs at a load average of about 6 (#74's gate).
- **Severity**: major (a flaky gate; a depth bound that held only under C2).
- **Evidence**: #74's gate logs (`74-irdepth*.log`); #86's red `-Xbatch -XX:TieredStopAtLevel=1`, 5
  of 5 overflows (`.logs/86-irdepth-red.log`).
- **Change made** (#86): `lower` only tests the kind and passes it on; `built` does the spend, the
  level check and the switch; every Resolver Stub goes through `stub(Object...)`, too large for C1
  to inline. Warm C1 fits 512 levels in 480 KiB. `IrDepthTest` runs its child a second time under C1
  only, with the same limits and expectations. The margin for 500 value parameters under C1 is thin
  (480–512 KiB); #93 removes their per-part depth (ADR-0043).
