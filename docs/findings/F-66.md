# F-66 — The JDK's root locale has no zone abbreviations

- **Assumption**:
  - ADR-0017 "Sandbox": "Date formats use the root locale."
  - Spec 4's draft, question 5: `%Z` is the JDK's short zone name in that locale.
- **How it fails**:
  - A (tzdb 2026e on JDK 25.0.5): `Locale.ROOT` gives `GMT+09:00` for Asia/Tokyo, so the draft's
    assumption fails.
  - `Locale.ENGLISH` gives `JST`, `EST`/`EDT`, `IST` and `CET`. It gives `GMT+04:00` for
    Asia/Dubai, where jq-ref prints `+04` (P4). It never gives `LMT`, which jq-ref prints for an
    LMT era (P4: `LMT +0918`).
  - `strftime` prints `GMT` in every zone (P4; A: `localtime|strftime("%H %Z %z")` →
    `17 GMT +0000` under America/New_York).
- **Severity**: major (every `%Z` under a named zone would differ from jq-ref).
- **Evidence**: spec 4 grilling round 1, question 5 (`docs/wayfinder/spec-4-grilling.md`).
- **Change made** (spec 4, ADR-0052):
  - Names of days, months and AM/PM come from fixed English tables. ADR-0017's "Date formats use
    the root locale" is replaced; jq-ref showed no locale effect (ADR-0020).
  - `%Z` is the JDK's `Locale.ENGLISH` short name. A `GMT±hh:mm` name prints as `±hh[mm]`,
    tzdata's numeric form.
  - `DEVIATIONS.md` gains "zone abbreviations": LMT eras, zones that tzdata names differently from
    the JDK, and the tzdata version. The host-zone ticket finds those zones by running jq-ref under
    each `TZ`.
  - A TZif name reader can replace the JDK's names later without rework.
