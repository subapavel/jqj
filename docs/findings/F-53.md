# F-53 — Order's key-list sort is uncharged, against F-48's reason

- **Assumption** (ADR-0037 "Ticks"): "its scratch key orders are not charged" (design approval O1).
- **How it fails**: F-48 later made a sort's compares tick because an uncharged sort of n long
  strings escapes the step budget (ADR-0008). `Order.java:192` still sorts each object's key list
  with `List.sort` and charges nothing, so comparing two objects of many long keys does
  O(n log n · key length) uncharged work.
- **Severity**: minor (no crafted case in 2a's tests; bounded by the document).
- **Evidence**: spec 2a review (#56, reviewer-standards, jq-core).
- **Change made**: none in 2a. Ticket #104 decides between ticking through jqj's merge sort and
  reusing the key proof's sorted keys (ADR-0044), then amends ADR-0037's sentence. ADR-0037 points here.
