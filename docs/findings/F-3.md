# F-3 — No second reading mode; the reader classifies UTF-8 rather than validating it

- **Assumption** (founding architecture §13 risk 6, and §10): add a second, light reading mode if
  the tape costs much more than a forward cursor; the reader "validates" its input.
- **How it fails**:
  - The only large win, stopping at the field, changes results: jq takes the last duplicate key
    and rejects malformed input anywhere (Spike B, #4).
  - jq-ref accepts invalid UTF-8 and replaces it with U+FFFD, and prints DEL as `\u007f` (observed
    on #5). The reader must classify such strings (tag 6), not reject them.
- **Severity**: minor.
- **Evidence**: `bench/RESULTS.md` "Spike B" and "Tape reader for milestone 1"; issues #4 and #5.
- **Change made**: the owner chose one validating reading mode (#4), and ADR-0002 defines tag 6.
  §13 risk 6 is answered, and §10's "validates" reads as "validates JSON grammar, classifies UTF-8".
  Whether lone surrogates, a BOM, `nan` or `Infinity` are accepted is left to "How do the JSON
  reader and writer behave?" (#11).
- **Closed** by ADR-0015 (issue #11): `nan`, `Infinity` and lenient tokens are accepted, a lone high
  surrogate is an error and a lone low one U+FFFD, a BOM is stripped at the start of the input stream.
