# F-40 — Iterating a read object costs n² steps, because a view cannot tell a repeated key

- **Assumption** (ADR-0002 tape entry, ADR-0004 views, ADR-0008 ticks): a view's walks are linear,
  and a native loop charges ticks for the entries it steps.
- **How it fails**: jq keeps the last value of a repeated key, in its first place. An `ObjectView`
  holds the tape's members in source order, repeats included, so `.[]` must scan the earlier keys
  for every member (`isFirst`) and the later ones for its value (`lastValueOf`). A linear walk
  needs a set of seen keys, which the hot-path rule forbids. #63 charges every comparison, so
  `.[]` over n distinct keys costs n² + n − 1 steps: correct and bounded, but slow for wide objects.
- **Severity**: major (speed; a 10⁴-key object costs 10⁸ steps).
- **Evidence**: #63 review (standards FAIL on the untimed scans); `ObjectView.java` at 8d6bab2;
  `NavigationBudgetTest` object pairs.
- **Change made**: #63 charges the scans. The reader does not hash or compare keys today (its
  premise above was wrong, #82 design), so #82 adds a bounded proof at an object's close and tags
  a proved object 10 (ADR-0002 amendment), under the owner's ~10 % reader-cost line. The writer's
  key walk on read objects was an untimed n² too; #82 ticks it on tag 9.

## 2026-11-13: fix withdrawn

#82's implementation of the ADR-0002 amendment went over its cost bar: reader +12 % (100 KB) and +26 % (10 MB) against 5ab4aa7, and 2.59x on the flat 78 841-key object. The amendment is withdrawn, and the finding stays open. Read-object iteration remains n². Correction (2026-11-13): the n² is not fully ticked on the integration branch. The Printer's key scan and ObjectView `size()`/`forEach` charge no tick (the Printer's tick exists only on the unmerged `t/82-distinct-keys`), so a budget does not bound every walk.

## 2026-11-13: owner decision

The owner chose option D from the grilling-adviser's recommendation on #82: a read object's walk proves its keys distinct once, at the start of its first walk, in a table reused from the Workspace. The tape stays read-only and the reader pays nothing. The reason: Flottila is an integration platform still in development, so object widths cannot be predicted and inputs may be crafted. #82 is closed as not planned; #85 builds the walk-side proof, adds the missing ticks and replaces #68's local Detach copy. The finding stays open until #85 merges.

## 2026-11-13: change made (#85, ADR-0044)

Every walk of a read object begins with `KeyProof.walk`, pairwise up to 8 keys, then a table in `RunState.ints` with a 4 n probe budget and jqj's merge sort past it, one tick per key entry and per sort compare; `.[]` over n distinct keys costs 2 n steps after the read tick (41 at 20 keys, `NavigationBudgetTest`), 10^5 keys and 2^15 colliding keys walk within `WideObjectTest`'s 5 s, and the Printer's walk and the host's `size()`/`forEach` are linear too.
