# F-40 — Iterating a read object costs n² steps, because a view cannot tell a repeated key

- **Assumption** (ADR-0002 tape entry, ADR-0004 views, ADR-0008 ticks): a view's walks are linear,
  and a native loop charges ticks for the entries it steps.
- **How it fails**: jq keeps the last value of a repeated key, in its first place. An `ObjectView`
  holds the tape's members in source order, repeats included, so `.[]` must scan the earlier keys
  for every member (`isFirst`) and the later ones for its value (`lastValueOf`). A linear walk
  needs a set of seen keys, which the hot-path rule forbids. #63 charges every comparison, so
  `.[]` over n distinct keys costs n² + n − 1 steps: correct and bounded, but slow for wide objects.
- **Severity**: major (speed; a 10⁴-key object costs 10⁸ steps).
- **Evidence**: #63 review (standards FAIL on the untimed scans); `ObjectView.java` at 8d6bab2;
  `NavigationBudgetTest` object pairs.
- **Change made**: none in #63 beyond charging the scans. The fix is the reader's: when it builds an
  object's tape entry it knows whether any key repeats, so a flag (or a deduplicated member list)
  lets the walk skip both scans. That amends ADR-0002 and is filed as its own ticket.
