# F-29 — The compile-mode oracle runs after every merge, not only at the spec gate

- **Assumption** (F-27 "Change made"; ADR-0020 "The compile-mode and backend oracles"): the
  compile-mode oracle, once built, runs only in the spec gate, because the ticket gate's step 1 is
  over its 60 s target.
- **How it fails**: spec 2 adds the analyses one class-C ticket at a time (cardinality with
  may-break-out and the value form, then folding, specialisation, tail calls). A fact that is wrong
  but passes the ticket's facts test would show only at the spec gate, up to about ten merged
  tickets later, when the culprit is no longer obvious. ADR-0020 itself rejected "pass lists once
  per spec" for the same reason. The oracle tests cost about 2.7 s of step 1 at #40.
- **Severity**: major (it decides when a wrong analysis fact is caught).
- **Evidence**: spec 2 grilling round 1, Q3 (owner yes, 2026-11-12); #40 and `bench/RESULTS.md`
  "Ticket-gate steps (#40)".
- **Change made**: the ticket gate stays as F-27 left it. The verifier runs the compile-mode oracle
  on the integration branch after every merge, beside `regen --oracles` (ADR-0020), and a
  disagreement stops the next merge until it is fixed. The spec gate still runs it in full.
  ADR-0020 is amended to point here.
- **Amended by F-46 (#89)**: the ticket gate now runs the compile-mode oracle too, because a regression seen only after merge broke the integration branch (F-46).
