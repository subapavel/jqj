# F-76 — The census misses `fromjson`'s replay cases and a lenient token in an input

- **Assumption**:
  - GLOSSARY "Case census": a case goes to the spec that makes it pass, "from the builtins and
    constructs its filter reaches in the reference jq".
  - Spec 4 grilling, question 2 and M3: `fromjson` is built in spec 4 for strict text; malformed
    text and lenient tokens wait for spec 5's replay.
- **How it fails**:
  - A filter does not show what its text or its input needs. `fromjson` is a spec-4 builtin, yet
    these cases need a lenient token or the replay:
    - jq.test 2315: `fromjson | isnan` on `"nan"`;
    - jq.test 2324: NaN payloads under `try`;
    - jq.test 2498: `"{'a': 123}"` → "Invalid string literal; expected \", but got ' at line 1,
      column 5 (while parsing '{'a': 123}')".
  - jq.test 2319 (`tojson | fromjson` on `{"a":nan}` → `{"a":null}`) needs a lenient token in its
    input document, which no scan of the filter sees.
- **Severity**: minor (spec 4's gate would require cases it cannot pass).
- **Evidence**: spec 5 grilling round 1, A3; `jq.test` 2315, 2319, 2324, 2498; spec 4 grilling M3.
- **Change made**:
  - The census (`scripts/census.java`) gives jq.test 2315, 2319, 2324, 2498 and 2563 to spec 5
    (2563, `fromjson` past the depth limit, was already spec 5's by spec 4's M3). They go to 5a's
    ticket for `fromjson` through the replay.
  - A sweep for other spec-4 census cases that need a lenient token or a replay text stays open.
  - ADR-0023 is amended. On the adviser's list for the owner (2026-11-16).
