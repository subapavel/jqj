# F-48 — A sort's comparisons tick; the count is fixed by jqj's own merge sort

- **Assumption** (ADR-0037 "Ticks"): "A sort's comparisons are never ticked, so counts do not depend
  on the sort."
- **How it fails**: the first two orderers tick inside their compares. `keys` (#72, `Keys.java`)
  ticks once per compare of its key sort, at least 1 and one per started KiB of the shorter key.
  `sort` and its kin (#73, `Sort.java`) tick once per member read and add each compare's own
  ADR-0037 ticks (member pairs, KiB of strings). A sort without compare ticks leaves a sort of n
  long strings or deep containers, O(n log n · size) work, outside the step budget (ADR-0008).
- **Severity**: minor
- **Evidence**: #73 review at bf12159; `SortStepsTest` (it pins 3 compares), `NativeStepsTest`
  (`keys`).
- **Change made**: a compare inside a sort ticks as any compare does (ADR-0037). The count does not
  depend on the backend or the platform sort: it is the compare sequence of jqj's own stable merge
  sort (ADR-0012), which both backends share, and the tests pin it. A change to that merge sort
  changes counts and is checked by `SortStepsTest`. ADR-0037's status line names this finding;
  ADR-0034's tick list states the #72 and #73 rates.
