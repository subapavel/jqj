# F-67 — `strptime` and `strftime` read the host zone for `%s`

- **Assumption**:
  - ADR-0017 "Sandbox": "`localtime` and `strflocaltime` use the host zone, UTC by default; …
    `mktime`, `gmtime` and `strftime` are UTC in both." `strptime` is in neither list.
  - Spec 4's draft: `strptime` is pure and is built with `gmtime`, `mktime` and `strftime`.
- **How it fails**:
  - A: `"1425599507"|strptime("%s")` → `[2015,2,5,23,51,47,4,63]` under `TZ=UTC` and
    `[2015,2,6,8,51,47,5,64]` under Asia/Tokyo. The broken-down time is the local one, so `%s`
    reads the zone.
  - `strftime("%s")` does too (architect, jq-ref 1.8.2, 2026-11-14): `0|strftime("%s")` → `"0"`
    under `TZ=UTC` and `"-32400"` under Asia/Tokyo; `0|gmtime|mktime` → `0` under both, so
    `mktime` stays UTC.
  - Its result therefore depends on the host, which makes it a zone reader and not pure (spec 3's
    Facts). Its cases under Asia/Tokyo and America/New_York (GATE check 1) would show it.
- **Severity**: minor (one conversion of one builtin; the sandbox's UTC default hides it).
- **Evidence**: spec 4 grilling round 1, M2 (`docs/wayfinder/spec-4-grilling.md`).
- **Change made** (spec 4, ADR-0052):
  - ADR-0017's zone readers gain `strptime` and `strftime`, each for `%s` only: it uses the host
    zone, UTC by default.
  - `strptime` and `strftime` declare themselves not pure, as `localtime` and `strflocaltime` do.
  - `%s` is built with each table under the run's zone, which is UTC until the host-zone ticket
    builds the host zone; the `TZ=UTC` cases are the strftime and strptime tickets' reds, the
    Asia/Tokyo ones the host-zone ticket's (grilling-adviser, spec 4 ticket approval).
  - Under the sandbox the host zone is UTC, so a filter still cannot read the system zone (GATE
    check 7).
