# F-44 — The inline cap bounds node count, not IR depth; only field runs are flat

- **Assumption**:
  - ADR-0040 "Inline cap": a node count (`INLINE_CAP = 65 536`) and an expansion nesting of 512 keep a compile bounded.
  - F-42 "Change made": #70 lowers path chains with a loop, so a chain of any length compiles and runs.
- **How it fails** (the #70 standards review at de34e3f; both NOT_RUN, the red must observe them):
  - **Inlining multiplies depth.** 300 defs `def fi: [`×100 `f(i-1)` `]`×100, called as `f300`, stay under both caps (about 30 001 nodes and 300 expansions), yet the inlined Collects nest about 30 000 deep. `lower`, `IrVerifier` and `Compiler` recurse on the IR, and F-42 overflowed at about 44k frames on the 512 KiB stack of ADR-0017.
  - **Only field reads are fused.** `Resolver.chain` fuses runs of `.a` into one `FieldRun`. Any other step kind (`.[0]`, `.[]?`, slices) still builds a left-nested Pipe as deep as the chain, and the same recursive passes walk it. jq-ref accepts 21 844 steps of `.[0]` (rc 0, the #70 spec review).
  - **No DEVIATIONS row for long def runs.** jqj compiles any number of top-level defs, but jq-ref rejects 10 000 with `memory exhausted` (DefChainTest javadoc).
- **Severity**: blocking for #70 (an untrusted filter can crash the compiler, the F-42 class).
- **Evidence**: the #70 standards review at de34e3f; Resolver.java `expand`, `chain`; IrVerifier.java:112; Compiler.java:82.
- **Change made** (#70):
  - The resolver tracks the IR depth it builds. Past `Resolver.MAX_IR_DEPTH = 512`, the filter is a Stub, like the 512th nested expansion. A DEVIATIONS row records it, since jq runs such filters; spec 2b's calls revisit it.
  - The number was first ruled 4 096. #70 measured nested Collects through defs on a 512 KiB thread: cold, 625 levels run and 650 overflow; warm, 4 096 run and 8 192 overflow (probe at f7670a7). A cold JVM is the case a host meets, so the bound is 512, the parse depth (#81), with margin under 625.
  - Every step kind of a postfix chain lowers to an IR whose depth does not grow linearly with the chain, with tick counts equal to the nested form.
  - DEVIATIONS gains the long def run row, and the "Long path chains" row names the step kinds its tests cover.
  - ADR-0040 is amended in the same merge.
- **Not changed here**: Binder and Resolver still recurse on left-associative operator chains (`.a+.a+…`, `and`, `or`), which the parser builds in a loop. That existed before #70 and is ticketed separately.
