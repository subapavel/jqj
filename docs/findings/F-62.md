# F-62 — WALK keeps its walk state in the Update's hidden frame slots, not on the Workspace path stack

- **Assumption**: ADR-0010 "Shapes": "WALK rebuilds along the steps with the Workspace path stack".
  The glossary's Workspace holds a "path stack".
- **How it fails**:
  - A WALK Update's right side may raise into a `Try`, break to a `Label`, be retried by an
    `AltBind`, or suspend on the trampoline. jq-ref runs `walk(.)` (builtin.jq defines it through
    `|=`, ADR-0023) on a 20 000-deep value.
  - A Workspace or RunState stack would need its height restored at each of these, the cost
    ADR-0010 rejected for TRACKED. It would also pin keys between runs (ADR-0034).
  - Collecting the paths first does not avoid the state: on jq-ref
    `[1,2]|(.[]|debug("L")) |= (debug("R")|.+1)` prints L, R, L, R.
- **Severity**: minor (no wrong value yet; the stack's restore points were never built).
- **Evidence**: spec 3 grilling round 1, question 11; round 2, question 3 and A2.
- **Change made**:
  - Walk state lives in the Update's hidden frame slots (ADR-0045's count): none for a chain
    without `.[]`, one cursor per `.[]` level entered, never one per element.
  - An Update sets the slots at entry and clears them at its end; an abandoned run restores
    nothing.
  - A heap form works on its activation's cells and a recursive right side has its own frame, so
    the state survives a suspension.
  - ADR-0010's WALK bullet and the glossary's Workspace are amended; ADR-0030 is not.
